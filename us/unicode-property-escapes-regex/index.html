Unicode Property Escapes in Regular Expressions: Scripts, Categories and Sets

Engineering guide to JavaScript regex Unicode property escapes, General_Category, Script_Extensions, /u and /v modes, text validation and edge-case tests.

Technical referenceUnicode baseline: 18.0.0Updated 26 October 2026

A Unicode-aware regex is more than an ASCII character class

A regular expression such as [A-Za-z] matches a subset of Latin letters. It excludes ordinary letters from Greek, Cyrillic, Arabic, Devanagari, Thai, Japanese and many other writing systems. Similarly, \w can have engine-specific definitions and is not guaranteed to mean “every Unicode letter.” Unicode property escapes offer an explicit way to match characters by published Unicode Character Database properties.

In ECMAScript, the \p{...} escape matches values of binary Unicode properties or enumerated property values when the regular expression has Unicode-aware u or v mode. Its complement is \P{...}. These classes can recognize letters, combining marks, scripts, numbers and more, but they still operate over the engine's Unicode property data version and the semantics of its matching mode.

JavaScript intentionally requires the property name for script matching (for example Script=Greek) rather than interpreting an unqualified Greek escape as a script shortcut. The exact supported properties and aliases follow ECMAScript specification tables; other regex engines, including ICU, PCRE and Python third-party libraries, have their own Unicode-property syntax.

General_Category versus binary derived properties

General_Category partitions Unicode characters into classifications such as Lu (uppercase letter), Ll (lowercase letter), Mn (nonspacing mark), Nd (decimal digit), and others. A binary property such as Alphabetic has its own definition and is not necessarily identical to General_Category=Letter. A mark can participate in alphabetic behavior depending on the particular derived property.

Validation rules should therefore use the property that actually models the domain rather than choosing whichever sounds similar in English. Checking \p{Letter} for an identifier might reject combining marks used in legitimate names; checking \p{Alphabetic} may include a broader repertoire than expected. A real identifier profile must combine properties, contextual rules, normalization and security restrictions.

Script is not a language detector

The Unicode Script property identifies a primary script assignment; Script_Extensions records a set of scripts for characters used with multiple writing systems. Common punctuation and inherited combining marks may not have a single useful language-specific script assignment. In multilingual text, a string mixing Latin and Greek letters is valid Unicode even if a particular application disallows that mixture in identifiers.

const greek = /\p{Script=Greek}/u;
const latin = /\p{Script=Latin}/u;
console.log(greek.test("Ω")); // true
console.log(latin.test("A")); // true
console.log(greek.test("A")); // false
console.log(/\p{Letter}/u.test("Ж")); // true
console.log(/\p{Decimal_Number}/u.test("٣")); // true

These tests establish script and category membership, not human language. The letter A occurs across numerous languages that use the Latin script. Restricting identifiers to a script still needs policy for Common and Inherited characters and for combinations that create visually confusable names.

Unicode-aware /u versus the newer /v mode

ECMAScript's u flag enables Unicode-aware parsing and code-point semantics for character-class matching. The newer v flag (Unicode sets mode) adds expressive set operations for character classes and supports certain Unicode properties of strings, allowing matches of some finite multi-code-point sequences defined by standard properties. The two flags are mutually exclusive on one expression.

Because property-of-string support and set notation are newer, test compatibility with the actual runtime and deployment targets. /\p{RGI_Emoji}/v can recognize a supported property-of-strings repertoire in engines that implement it, but this is not equivalent to UAX #29 grapheme segmentation or a complete definition of every user-perceived emoji sequence.

const letters = /\p{Letter}+/gu;
console.log("A Ω Ж 3".match(letters)); // ["A", "Ω", "Ж"]
const digits = /\p{Decimal_Number}+/gu;
console.log("012 ٣٤٥".match(digits)); // ["012", "٣٤٥"]
// Use the v flag only where supported by the target ECMAScript runtime.
// Do not treat property-of-strings matching as a grapheme segmenter.

Complement classes, case folding and misleading assumptions

Case-insensitive matching changes how complements can behave, and the order of case folding relative to complement operations differs between certain u and v constructions. The ECMAScript specification, not a generic set-theory intuition, determines these results. A dangerous assumption is that \P{Letter} automatically means “nonword character” in every regex mode and application locale.

A combining mark can be part of a grapheme cluster despite not belonging to General_Category Letter. Conversely, a mathematical styled letter may be in a letter category but fold under compatibility normalization to an ordinary Latin letter. Unicode property checks and string normalization are different transformations and should not be conflated.

Script restrictions and Unicode confusables

For username validation, a regex that accepts only \p{Letter} and \p{Number} is not enough to prevent impersonation. Latin A and Greek capital Alpha are distinct code points with similar shapes. Unicode Technical Standard #39 defines security-relevant guidance including confusable mappings, mixed-script analysis and identifier profiles. Property-based allowlists are one component of a broader policy.

Normalization should happen in a defined order relative to validation. NFKC can map a compatibility styled character to ordinary text; if the validator sees only one representation but the system compares another, identity collisions or bypasses can result. Preserve original source text where user-facing fidelity matters, especially when the US Fancy Text tool provides copyable mathematical alphabets for experimentation.

Python re is not JavaScript property escape syntax

Python's standard re module does not implement \p{...} Unicode property escapes as JavaScript does. Its \w matches a Unicode-aware set of alphanumeric characters and underscore under default string semantics, but this is not a complete UAX #29 word segmenter. A dedicated Unicode-property engine or ICU binding is needed for parity with the exact ECMAScript property semantics.

import re
assert re.fullmatch(r"\w+", "abc123") is not None
try:
    re.compile(r"\p{Script=Greek}")
    raise AssertionError("built-in re unexpectedly accepted \\p")
except re.error:
    pass
