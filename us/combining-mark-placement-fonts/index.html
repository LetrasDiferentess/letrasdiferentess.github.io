Combining Mark Placement in Fonts: Anchors, GPOS and Canonical Order

Trace base-to-mark and mark-to-mark attachment, canonical combining classes, OpenType GPOS anchors and cross-font failures in Unicode typography.

Technical referenceStandards-aware implementation guideUpdated 26 October 2026

Combining marks are encoded characters with their own Unicode properties, but their visible positions usually depend on glyph shaping and font layout. A mark can be present in the string and still look detached if the font lacks suitable anchors or the renderer splits a cluster across font runs.

The sequence of code points is not a drawing instruction

The text é contains LATIN SMALL LETTER E followed by COMBINING ACUTE ACCENT; U+00E9 contains the precomposed LATIN SMALL LETTER E WITH ACUTE. These are canonically equivalent under Unicode normalization, but they are different encoded sequences before normalization.

A shaper may use an existing precomposed glyph, decomposed glyphs with anchors or fallback methods. The fact that both render as a familiar accented letter does not establish whether the source contains one scalar or two. Preserve code-point annotations in bug reports.

Canonical combining class helps define ordering

Unicode canonical combining class supports a canonical ordering of many nonspacing marks. During normalization, marks with distinct nonzero combining classes can be reordered where the algorithm allows it, while other relationships stay constrained. This is about stable text representation, not automatically arranging visible accents on a canvas.

For example, combining marks can have different canonical combining classes, and their canonical order matters to NFC/NFD equality. A font may still place them poorly even after correct normalization because font anchoring and layout are separate requirements.

Base-to-mark positioning uses anchors

OpenType GPOS MarkToBase attachment associates a mark glyph's anchor with a base glyph's anchor. The shaping output may give the mark a near-zero advance plus an offset so the diacritic sits at the expected position. Merely drawing the mark after the base at the current pen coordinate will not reliably reproduce the intended placement.

A font's anchors are design data, and different fonts can use different positions while remaining valid. When visual alignment breaks, inspect glyph IDs, GPOS lookup application, offsets and selected font face before attempting CSS letter-spacing workarounds.

Mark-to-mark attachment handles stacked marks

In words with multiple combining diacritics, mark-to-mark positioning can attach one mark to another. This becomes important for scripts and orthographies that use stacked accents. A base font that supports one isolated accent may not provide all mark classes or anchors needed for longer sequences.

If the second accent overlaps the first, the problem can be a missing MarkToMark lookup or a run split, not necessarily illegal Unicode input. Test both isolated pairings and realistic words. The same scalar sequence can look different if the selected font faces have different anchoring capabilities.

Fallback font splits can destroy attachment context

Suppose the primary font has a base letter but no relevant combining mark. A platform might choose fallback to cover the sequence, split glyph runs or apply synthetic combining behavior. There is no universal guarantee that two unrelated fonts share compatible anchor geometry.

When a mark is detached, use diagnostic tools to check the fonts assigned to the whole grapheme cluster. For high-fidelity applications, avoid splitting a complex sequence between faces if a suitable single font supports its shaping. A CSS unicode-range split needs tests with decomposed text as well as precomposed samples.

Grapheme boundaries and shaping clusters serve different needs

UAX #29 extended grapheme cluster rules usually keep a combining mark with its base for default cursor movement. A shaping engine may merge or reorder glyph clusters according to its own documented rules. The segmentation boundary is a user-interface abstraction, while attachment and advance are font-level rendering decisions.

An editor that deletes only U+0065 and leaves U+0301 behind can produce an orphan accent. A renderer that draws correct clusters but positions the accent poorly has a different defect. Treat editing and glyph placement as distinct issues in verification.

Normalization cannot repair a broken GPOS table

NFC may compose certain sequences when a precomposed character exists, but does not guarantee every combination has a precomposed representation. NFD decomposes precomposed characters into canonical components where applicable. Neither operation adds missing anchors or corrects a flawed font layout table.

Normalize when the application's data equality or storage contract requires it, not as a blind graphics repair. Compare NFC and NFD inputs explicitly to isolate whether shaping treats canonically equivalent forms consistently for the target font and script.

Debug with glyph positions and code point vectors

Capture U+0065 U+0301, U+00E9 and cases with two combining marks. Log the original scalars, normalization form, actual font selected, shaped glyph IDs, advances and x/y offsets. Reproduce at multiple scales to distinguish placement errors from raster clipping.

If offsets and glyph IDs match but the top accent is cut off, investigate line boxes, clipping and rasterization rather than rewriting text. If offsets differ unexpectedly between equivalent sequences, isolate the font and shaping configuration. Always preserve the original corpus fixture.

Reproducible experiment with fully specified input

Preserve the exact Unicode sequence before running the example. For browser comparisons, record the destination application, browser build, font files if relevant, system locale and any optional editor transformations. The example tests representation-level facts; it does not on its own demonstrate that every browser or native application must produce the same visual output.

const composed = '\u00E9';
const decomposed = 'e\u0301';
console.log(composed.normalize('NFD') === decomposed); // true
console.log(decomposed.normalize('NFC') === composed); // true
console.log([...decomposed].map(c => 'U+' + c.codePointAt(0).toString(16)));
// Test both forms against the same font, font size and shaping features;
// record mark glyph x_offset, y_offset and advance.

A reliable technical report separates the original input, the representation delivered to an API and the outcome visible to the user. When a copy/paste or rendering test fails, retain the raw specimen and compare successive representations so that display-only differences do not get mislabeled as encoding changes.

Include adversarial and multilingual input, not only a short English word. Save code-point lists, serialized bytes when available, input method context, observed UI behavior and environment metadata. Repeat after browser, editor, operating-system or font updates; changes in renderer behavior do not imply that source strings were modified.
