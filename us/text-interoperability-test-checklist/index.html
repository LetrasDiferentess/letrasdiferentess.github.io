Text Interoperability Test Checklist: A Cross-Platform Unicode Verification Framework

A complete acceptance framework for Unicode fidelity across editors, encodings, browsers, clipboards, storage, search, rendering, accessibility and security.

Technical referenceUnicode and cross-platform API methodsUpdated 26 October 2026

Text interoperability is end-to-end behavior: a Unicode string travels through keyboards, browsers, DOM editing, clipboard MIME types, encoders, persistence, search and display. A system can pass every isolated unit test yet corrupt text at one integration boundary. This framework organizes the evidence needed to certify particular workflows without claiming that one screenshot or one normalization test establishes universal Unicode support.

Define what must be preserved at each boundary

Some workflows promise exact Unicode scalar identity; others permit NFC canonical normalization; visual editors may intentionally transform formatting while preserving semantic text. The first acceptance criterion is a written contract identifying which differences are permitted.

For each transfer, record source, destination, encoding, MIME type, locale, error policy and intended output. Do not use 'looks the same' as the only condition for lossless exchange: mathematical symbols and variation selectors can disappear without a visible clue.

Validate decoding and encoding before text algorithms

UTF-8 should reject or explicitly replace malformed byte sequences according to a documented policy. UTF-16 handling must avoid unpaired surrogates. JSON, CSV and HTML character references introduce different serialization syntax on top of encoding.

Capture raw byte fixtures and decoded code-point arrays. A non-ASCII character becoming U+FFFD is a decoding or conversion issue, while a well-formed decomposed accent changing under NFC can be an intentional normalization choice.

Check normalizations, case mappings and search behavior

NFC/NFD canonical equivalence, NFKC compatibility mappings, locale-sensitive Turkish I handling and Unicode case folding can produce different comparison keys. Collation additionally depends on language rules and ICU/CLDR data.

Declare the comparison contract and version. A database that normalizes usernames differently from the application tier can create duplicate or unreachable identifiers; a search index that applies NFKC may intentionally match more strings than strict byte equality.

Verify cursor, selection and grapheme boundaries

A user-facing editor should ordinarily avoid splitting a base-plus-mark sequence, emoji modifier or ZWJ cluster during common caret movement and deletion. DOM Range offsets and JavaScript length are measured in UTF-16 units rather than grapheme clusters.

Use UAX #29 fixtures and actual keyboard selection/undo tests. Validate IME input with real Japanese, Chinese and Korean keyboards; synthetic key events do not exercise the platform's composition path.

Audit rich-text and clipboard MIME variants

The clipboard may offer text/plain and text/html simultaneously. HTML-to-plain-text conversion can change paragraph boundaries, list markers, anchor destinations and table separators even while preserving visible words.

Test both MIME representations, selection shapes, Unicode scalars and paste preference into multiple destinations. Sanitizing untrusted rich HTML is a separate security responsibility; never confuse it with Unicode normalization or plain-text copying.

Exercise font fallback and complex-script shaping

Unicode code points identify characters, but fonts and shaping engines supply glyph IDs, positioning and color emoji support. Arabic joining, combining accents, ligatures, mathematical alphanumerics and emoji ZWJ sequences challenge simplistic one-code-point-one-glyph assumptions.

Record target font versions and renderer platforms. A box glyph or detached accent with intact text is usually a rendering/coverage concern, whereas a missing U+200D after copy is a data integrity failure.

Test bidi, vertical writing and language metadata

RTL Arabic or Hebrew paragraphs may contain Latin IDs and numbers; vertical Japanese uses different block progression and glyph orientation. HTML lang, dir, bdi and CSS logical properties influence presentation without changing scalar identity.

Verify logical storage order, copied text, focus order, line wrapping, accessibility reading order and punctuation. Do not reorder code points manually to fix a layout screenshot.

Test emoji semantics and accessible alternatives

UTS #51 RGI sequences may not render identically across system emoji fonts. CLDR annotations and screen reader speech can differ by locale and device. Mathematical styled Unicode can be semantically different from visually similar CSS formatting.

Check scalars and RGI membership first, then visual fallback and accessible naming separately. Critical UI states should not be conveyed only through pictographs; supply appropriate text, roles, names and state.

Apply field-specific input and identifier security

UAX #31 identifier syntax, UTS #39 confusable checks and IDNA/UTS #46 domain handling solve different problems. A valid mixed-language sentence should not be globally rejected as suspicious Unicode.

Test context-dependent join controls, default ignorables, confusable collisions and normalized-identity uniqueness under the actual product policy. Output HTML escaping and user verification must be tested separately from character classification.

Capture an actionable release-gate report

A mature test report lists every subsystem, tested environments, fixture data and versioned expected results, plus observed failures grouped by cause. It should distinguish hard failures such as corruption from approved variations such as different emoji artwork.

Require remediation or explicit documented acceptance for each difference. Preserve original fixtures so an upgrade can be reproduced, and rerun the end-to-end pipeline after any change to fonts, runtime Unicode tables, clipboard handling or storage schema.

Maintain long-term compatibility without freezing Unicode

Unicode and CLDR release new assignments and updated data; browsers, ICU and OSes adopt them on different schedules. A fixed regression corpus ensures old data remains supported while new feature tests document gradually expanding repertoire.

Test both present and legacy target environments. A platform lacking one new emoji image may still preserve its text correctly; a modernization project should avoid degrading existing text to support a new rendering feature.

Reproducible technical example

This controlled specimen demonstrates a single subsystem, not a comprehensive conformance claim. Use exact Unicode scalar values, record language/runtime versions and distinguish byte decoding, normalized equality, layout rendering and application validation. A visual match does not guarantee a reversible text interchange.

// A compact cross-platform text-integrity snapshot:
function snapshot(text){
 const segmenter=new Intl.Segmenter('en',{granularity:'grapheme'});
 return {codePoints:[...text].map(c=>c.codePointAt(0)),
  utf16Units:text.length,utf8Bytes:new TextEncoder().encode(text).length,
  graphemes:[...segmenter.segment(text)].length,nfc:text.normalize('NFC')};
}
for(const s of ['e\u0301','👩\u200D💻','🇺🇸','𝐀','مرحبا ABC']){
 console.log(snapshot(s));
}
// Run this at input, clipboard, storage and output boundaries and compare.

For reproducible defect reports, provide the original encoded data, the first observable transformation, the expected result and the tested API versions. The same logical text can produce different font glyphs, and an accidental scalar replacement can be invisible when those glyphs look alike.

Keep all expected outputs versioned rather than changing them automatically during upgrades. For byte-to-text errors use explicit strict or replacement policies; for identity checks use the actual standard named by the product.

Handling platform differences

An updated Unicode data version can introduce new assignments and properties, while font and OS support may lag. Test the actual deployed environments and record differences as supported variation, expected tailoring or defects. Preserving original input is critical to distinguishing these outcomes.
