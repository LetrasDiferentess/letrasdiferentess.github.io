Unicode Bidirectional Algorithm (UAX #9): Levels, Runs and Logical Text

Understand the Unicode Bidirectional Algorithm for mixed Arabic, Hebrew and Latin text, including directional classes, isolates, embeddings and resolved display order.

Technical referenceUnicode and web interoperabilityUpdated 26 October 2026

Bidirectional text has one logical code-point sequence and an independently resolved visual order. UAX #9 defines a Unicode algorithm for organizing left-to-right and right-to-left text into resolved levels and display runs. A screenshot showing reversed visual positions does not mean the underlying string was reversed.

Separate logical storage order from display order

A paragraph containing Arabic, Latin letters, digits and punctuation is normally stored in logical reading order. Rendering engines resolve directionality so the visible glyphs follow the applicable bidirectional behavior. Editing APIs, search and serialization must preserve the original sequence unless an explicit transformation is intended.

Writing Arabic letters in reverse Unicode order to make a preview look correct is a data error. That approach breaks copy/paste, cursor navigation and downstream search. The correct solution is a suitable paragraph base direction and appropriate isolation of embedded runs.

Character directional classes are inputs

UAX #9 assigns bidirectional classes such as L, R, AL, EN, AN, NSM, neutral classes and formatting controls. A character's script alone is not a reliable shortcut for its bidi class: digits and punctuation have distinct resolution rules.

Strong characters help determine direction in their context; weak and neutral characters are resolved using surrounding runs and algorithmic rules. A naive renderer that merely reverses all right-to-left characters will mishandle Arabic digits, punctuation and nested Latin phrases.

Determine paragraph direction before resolving runs

A paragraph has a base embedding level determined by a higher-level protocol, an explicit direction or a first-strong-style default where appropriate. CSS and HTML provide higher-level mechanisms for choosing base direction; the underlying Unicode algorithm then resolves directional behavior.

The base level affects how neutral characters align and how mixed content wraps. As a result, the exact same scalar sequence can display differently when inserted into a left-to-right paragraph versus a right-to-left block without any change in stored data.

Embedding and override controls require care

Unicode has explicit directional formatting characters that affect embedding levels and overrides. Historically, controls such as U+202A LEFT-TO-RIGHT EMBEDDING and U+202E RIGHT-TO-LEFT OVERRIDE have been used to influence ordering. Unbalanced or unexpected overrides can create confusing or deceptive displays.

For newly generated isolated fragments, UAX #9 recommends isolate-based mechanisms in appropriate contexts. Do not insert RLO just to force alignment of a mixed-script username. In security-sensitive displays, make invisible formatting controls inspectable and enforce a documented identifier policy.

Isolates prevent context leakage

U+2066 LEFT-TO-RIGHT ISOLATE, U+2067 RIGHT-TO-LEFT ISOLATE and U+2068 FIRST STRONG ISOLATE establish isolate contexts, closed by U+2069 POP DIRECTIONAL ISOLATE. These let inserted text be treated as an independent directional unit for surrounding resolution.

In HTML, <bdi> or elements with appropriate direction and isolation can often express this intent more safely than inserting literal controls into stored text. The right choice depends on whether markup or plain text is being produced. Isolates affect display behavior but should not be stripped blindly from legitimate multilingual input.

Numbers and neutrals produce surprising punctuation

European digits embedded inside Arabic prose often remain readable left-to-right while the enclosing run flows right-to-left. Colons, parentheses, slash characters and spaces can take direction from context, producing results that appear to move punctuation unexpectedly.

A test fixture should contain identifiers, dates, currency strings, email addresses and punctuation next to both Latin and Arabic or Hebrew text. Check the full paragraph and its base direction rather than evaluating a punctuation character in isolation.

Line wrapping applies after bidi level resolution

Paragraph-level resolution and line-by-line visual reordering are related but distinct stages in UAX #9. Text engines commonly use resolved levels to reorder runs within each displayed line after line breaks are determined. Separate lines can exhibit different visual boundaries.

Do not reorder code points in storage according to one line layout; wrapping width, font metrics and device scale can change where lines break. A sequence that is correct at desktop width must remain logically intact when reflowed on a narrow screen.

Mirroring is not reversing strings

Some paired punctuation can have mirrored glyph presentation in right-to-left contexts. Unicode bidi mirroring properties and font/rendering behavior support this without changing the actual scalar values of the original parentheses or brackets.

A copied opening parenthesis should remain the same encoded character even if its visible shape appears mirrored. Inspect code points and embedding levels when diagnosing a problem rather than relying on screenshots of paired symbols.

Make the bidi process testable

Store fixtures with the exact scalar stream, paragraph base direction, isolate boundaries and expected display behavior. Verify logical copy output, native selection and cursor movement. Add visual tests for neutrals, nested numbers and wraps.

For deeper conformance, use Unicode's BidiTest.txt and BidiCharacterTest.txt data for the chosen Unicode version. Capture the Unicode version and layout implementation; correctness should be assessed against the relevant algorithm, not an aesthetic expectation derived from English text.

It is not a substitute for fully exercising the target application with the appropriate language, platform input method and real user data.
