ICU Unicode Text APIs: BreakIterator, Normalizer2, Collator and Locale Data

Understand ICU's Unicode-aware APIs for normalization, segmentation, collation, locale services and versioned data, including interoperability tradeoffs.

Technical referenceUnicode and cross-platform API methodsUpdated 26 October 2026

International Components for Unicode (ICU) brings together implementations of Unicode algorithms and locale-sensitive services. Its APIs serve different purposes: Normalizer2 handles normalization, BreakIterator handles text boundaries and Collator orders strings according to collation data. Applications should not treat these components as interchangeable 'Unicode cleaners'.

Separate normalization, segmentation and collation

Normalization determines canonical or compatibility representations of text. Segmentation identifies character, word, sentence and line boundaries. Collation provides culturally and contextually appropriate sort orders and comparison keys. Each has a different contract.

A valid NFC conversion does not tell an editor where to place the cursor; a grapheme iterator does not produce a locale-aware alphabetical sort order; and a collation key is generally not suitable as a display string. Choose one API per problem.

Normalizer2 provides multiple normalization forms

ICU Normalizer2 supports normalization schemes including NFC/NFD and NFKC/NFKD; some implementations provide specialized comparison-oriented variants such as NFKC_Casefold. Operations can normalize strings and check if an input is normalized.

Use form-specific code and version-aware tests rather than applying an arbitrary normalization everywhere. Compatibility folding can change styled mathematical characters, which may be inappropriate for a text generator intended to preserve exact Unicode output.

BreakIterator implements boundary analysis

ICU's BreakIterator can segment grapheme-like character clusters, words, sentences and line break opportunities, with locale-sensitive tailoring. It does not generally return one item per Unicode scalar when in character mode.

Word and line break results depend on locale and dictionary availability for scripts without explicit spaces, including Thai. A browser's Intl.Segmenter may use ICU internally but can expose a different abstraction and different ICU data version.

Collator applies locale-aware comparison rules

Collator compares and sorts strings using ICU/Unicode collation data, with configurable strength and other attributes. This enables language-sensitive ordering that differs from byte order or JavaScript ordinal comparison.

Do not assume one sort key is stable across all Unicode or CLDR updates. Store original strings and reindex derived collation keys after changing locale data or comparator settings; otherwise uniqueness and pagination may change unexpectedly.

UnicodeSet and property access support inspection

ICU includes APIs for Unicode character properties and sets. These can classify Script, Script_Extensions, general category and many derived properties using the bundled UCD version.

A Script property identifies a writing system, not a user's language or trustworthiness. A security profile requires additional standards such as UTS #39, field-specific restrictions and collision policies.

Encoding conversion belongs at a different layer

ICU provides conversion facilities for character encodings. Conversion maps bytes into Unicode text or between encodings under declared error policies; it is not transliteration of language between scripts.

Avoid treating a conversion failure as a font fallback defect. With strict error handling, invalid byte sequences should be reported; replacement mode may insert U+FFFD. Record original bytes before attempting another conversion.

Locale identifiers and BCP 47 require careful mapping

ICU locale IDs can express language, script, region and keywords; modern APIs support relationships with BCP 47 language tags. Locale services use CLDR datasets and may provide fallback when a particular resource is unavailable.

A successful locale constructor does not mean every option is implemented exactly. Query resolved locale or API attributes and use appropriate language/script metadata; the locale does not alter the Unicode identity of stored strings.

C and C++ boundary offsets need explicit units

ICU's UTF-16-oriented APIs may expose offsets in 16-bit code units, while UTF-8-oriented APIs measure bytes. The C/C++ layer distinguishes UChar, UChar32 and encoded data buffers.

Never mix an offset from a UTF-16 BreakIterator with a UTF-8 byte-buffer index. Document conversions carefully, especially around supplementary emoji or decomposed combining marks; wrong offset units cause corruption even if segmentation itself is correct.

ICU/CLDR upgrades require regression plans

ICU bundles Unicode/CLDR data and library implementation versions; changes can alter word boundaries, case mappings, collation order and supported emoji properties. Cross-runtime tests should record the ICU and Unicode/CLDR versions.

Before upgrade, run a corpus of accented strings, mixed scripts, numeric collation, emoji ZWJ, sentence punctuation, Thai words and malformed input. Classify changes as normative data updates, tailoring changes or unexpected regressions.

Handling platform differences

An updated Unicode data version can introduce new assignments and properties, while font and OS support may lag. Test the actual deployed environments and record differences as supported variation, expected tailoring or defects. Preserving original input is critical to distinguishing these outcomes.
