Transliteration vs. Script Conversion: Unicode, Romanization and Reversibility

Compare transliteration, transcription and character-set conversion with examples from Greek, Cyrillic and Japanese, including loss of information and search implications.

Technical referenceResearch and implementation notesUpdated 26 October 2026

Transliteration maps writing systems; encoding conversion maps representations of the same characters. Confusing these operations can cause irreversible information loss. A Greek name romanized for a travel document, a Japanese word represented in Latin letters, and a UTF-8 text file decoded from bytes are three very different processes, despite all potentially ending as readable strings.

Define transliteration, transcription and encoding conversion

Transliteration generally maps written symbols of one script to written symbols of another according to a specified scheme. Transcription may prioritize approximate pronunciation over letter identity. UTF-8 decoding, by contrast, converts bytes into the same abstract Unicode scalar values represented by those bytes.

One language may have multiple approved romanization schemes, so a 'convert to Latin' function needs a named standard and language context. No universal Unicode algorithm infers an exact phonetic reading for arbitrary text from code points alone.

Cyrillic-to-Latin output depends on the scheme

The Russian letter Ж may appear as Zh under familiar English-oriented romanization, while other standards use different symbols or conventions. A naive character table can work for a constrained schema, but it does not capture every language using Cyrillic.

Do not assume the Unicode Script=Cyrillic property implies Russian. Serbian, Ukrainian, Bulgarian and other languages use overlapping but distinct inventories and orthographies. Language metadata, scheme and exception rules belong in the conversion contract.

Greek transliteration is not Greek Unicode normalization

The name Αθήνα may be romanized as Athína in a particular scheme. That is not equivalent to NFC, NFD, case folding or changing the font. The romanized string consists of different Unicode characters and normally cannot be transformed back uniquely without information.

A case-insensitive search index can store both source and romanized forms, but should preserve the original so rendering, quotation and proper names remain accurate. Search recall gains from multiple representations should not be mistaken for a reversible encoding mapping.

Japanese reading cannot be deduced from kanji alone

Romanizing kana under a defined scheme is relatively straightforward compared with romanizing arbitrary Japanese kanji strings, where multiple readings and contextual interpretation are possible. A language-aware tokenizer or lexical analysis may be needed before romanization.

Converting Japanese kanji directly to ASCII letter sequences with a character-by-character map will fail on ordinary words. Linguistic ambiguity is not an implementation bug that Unicode code-point properties can solve by themselves.

Round-trip guarantees must be stated explicitly

A conversion is reversible only if the chosen scheme and input constraints ensure a unique inverse. Romanization may merge distinctions between source characters or omit tones and diacritics. An ASCII-friendly output might be suitable for a search alias but not for archival identity.

Test collisions deliberately. Two source words that map to the same Latin output demonstrate why storing only the transliteration loses information. If the application needs round-trip safety, maintain the original Unicode source as a separate field.

NFKC and transliteration solve unrelated problems

NFKC converts characters according to Unicode compatibility mappings. It can map mathematical bold letters or fullwidth forms to their compatibility equivalents, but it is not a general Cyrillic-to-Latin or Greek-to-Latin transliterator.

For instance, U+FF21 FULLWIDTH LATIN CAPITAL LETTER A maps under NFKC to U+0041, while a Greek alpha U+0391 does not become Latin A under Unicode normalization. Lookalike glyphs remain different scalars and should be kept distinct in security-sensitive contexts.

Script conversion may describe orthography, not romanization

Some languages have standardized parallel orthographies in more than one script. Converting Serbian Cyrillic to Latin orthography involves language-specific rules, potentially digraphs and case behavior. It is not automatically the same thing as phonetic transcription or transliterating arbitrary Cyrillic text.

The phrase 'script conversion' is thus broader than transliteration in some product contexts. Define whether the target is linguistic spelling, search normalization, machine-readable identifiers or a standardized transliteration system. The correct mapping depends on that purpose.

Unicode confusables are not legitimate translations

Greek alpha U+03B1 and Latin a U+0061 can look alike in some fonts, but replacing one with the other is neither translation nor normal Unicode normalization. Blindly mapping visually similar characters can corrupt identifiers and facilitate spoofing.

For fraud or security review, use explicit confusable skeletons and identifier profiles under a documented security policy; do not present those skeletons as human-readable translations of the original content.

Architect a multilingual search index without discarding source

Store source text, explicit language/script metadata where known, and zero or more derived search aliases labeled with the transliteration scheme and version. Normalize and case-fold only according to the search policy, then evaluate false matches separately.

Rank exact native-script matches differently from lossy derived aliases when user expectations require it. Test proper names, mixed scripts, punctuation, accents and names with multiple common spellings. An ambiguous query matching several native words is a known consequence, not necessarily a bug.

Reproducible specimen and observable boundaries

The following controlled example tests one narrowly defined distinction. It cannot alone establish correctness of a complete multilingual application. Preserve the original Unicode scalar values, identify any normalization or transliteration performed, and separately inspect font rendering, selection, data serialization and user-interface behavior.

const source = 'Α';      // Greek capital alpha U+0391
const latin = 'A';       // Latin capital A U+0041
console.log(source === latin); // false
console.log(source.normalize('NFKC') === latin); // false
console.log('Ａ'.normalize('NFKC') === latin);    // true
// Romanization requires a named language-aware scheme, not NFKC.

For interop reports, record the input stream, chosen language or locale (if meaningful), browser or runtime version, relevant font files and output. When the outcome is only visually different, avoid changing source characters until the rendering or layout stage responsible for the mismatch has been isolated.

Conformance and regression testing

  1. UTF-8 decoding. Preserve a fixture containing bytes → scalars. Specify the Unicode version, application environment and expected observations. Verify that preserves intended characters if bytes valid; compare the actual code-point stream separately from appearance.
  2. Transliteration. Preserve a fixture containing Greek → Latin. Specify the Unicode version, application environment and expected observations. Verify that script mapping under a named scheme; compare the actual code-point stream separately from appearance.
  3. Transcription. Preserve a fixture containing pronunciation → writing. Specify the Unicode version, application environment and expected observations. Verify that may differ from symbol-by-symbol mapping; compare the actual code-point stream separately from appearance.
  4. NFKC. Preserve a fixture containing U+FF21 → U+0041. Specify the Unicode version, application environment and expected observations. Verify that compatibility conversion, not language translation; compare the actual code-point stream separately from appearance.
  5. Security skeleton. Preserve a fixture containing confusable mapping. Specify the Unicode version, application environment and expected observations. Verify that not a human transliteration or stable identifier; compare the actual code-point stream separately from appearance.

For broader coverage, exercise known difficult cases rather than only ASCII text: decomposed accents, supplementary characters, mixed direction, language-specific scripts and emoji sequences where relevant. Include expected negative results and document any product-specific tailoring. Keep fixtures stable and versioned so future Unicode or browser updates remain diagnosable.

Interpreting false positives

A difference is not automatically a failure. Some font and platform variation is permitted; conversely, two identical screenshots may hide distinct scalar streams. A reliable defect report cites the applicable rule, names the observed implementation layer, and demonstrates how its contract is violated without silently discarding the original text.
