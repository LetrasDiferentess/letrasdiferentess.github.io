Ligatures and OpenType Features: GSUB, GPOS and Text Semantics

Distinguish standard, discretionary and required ligatures from Unicode characters, and examine OpenType feature selection without sacrificing searchable text.

Technical referenceStandards-aware implementation guideUpdated 26 October 2026

OpenType layout features are instructions for choosing and positioning glyphs. They normally do not rewrite the Unicode string. This distinction is essential for preserving text selection, search, copy/paste, accessibility and editorial behavior when a font turns sequences of letters into joined forms.

A ligature glyph is usually not a ligature character

The common fi ligature substitutes one glyph for a sequence of U+0066 LATIN SMALL LETTER F followed by U+0069 LATIN SMALL LETTER I. The characters remain separately representable and searchable. Unicode also contains legacy presentation characters such as U+FB01 LATIN SMALL LIGATURE FI, but encoding a typographic preference using U+FB01 is not generally the best way to write modern plain text.

Compatibility normalization NFKC maps U+FB01 to the sequence fi, unlike NFC, which retains the presentation character. This demonstrates why glyph presentation and character identity should be designed separately.

OpenType lookup structure and feature tags

GSUB organizes substitution lookups; GPOS organizes positioning lookups; GDEF describes classes, attachment points and related metadata. Features such as liga, clig, dlig, rlig and kern enable different behaviors and may be conditioned on script and language systems. A font listing a feature does not ensure that all scripts or glyph sequences have relevant lookups.

The shaping engine chooses lookup order and feature applicability according to font data and script rules. Disabling a feature for decoration must not break required shaping for scripts that depend on contextual substitutions or mandatory ligatures.

Standard, contextual and discretionary ligatures

liga typically controls standard ligatures such as fi and fl where provided. clig supports contextual ligatures. dlig covers discretionary forms whose stylistic appropriateness depends on design and editorial preference; they are commonly off by default. rlig identifies required ligature behavior needed for correct rendering in relevant contexts.

These tags express intent rather than universal visual outcomes. A font may have no matching lookup, and feature defaults can differ across text engines or text environments. Always test the actual font and run rather than expecting a given feature tag to produce a fixed image everywhere.

CSS font-feature-settings and higher-level properties

CSS exposes font-variant-ligatures for common controls and font-feature-settings for explicit OpenType feature tags. The former is generally easier to author and reason about for typical design needs. A rule like font-feature-settings: 'dlig' 1 requests discretionary ligatures where the font provides them; it cannot synthesize missing glyphs.

High-level typography properties and explicit low-level feature settings can interact, so inspect computed styles and the font actually loaded. Do not assume font-variant-ligatures: none is a harmless workaround for complex-script failures without testing the script's required shaping behavior.

Caret placement and cluster mapping

A single ligature glyph may correspond to several source characters. Cursor positioning requires logical-to-visual mapping or ligature caret information rather than treating each glyph as a single character. OpenType GDEF can supply ligature caret positions, but software may use its own fallback approximation.

This matters for text selection inside words, editor hit-testing, spell checking, and selection highlighting. If a user cannot place the cursor between the two letters of fi, the visible ligature alone does not explain the editor's behavior; inspect the editor's mapping between character offsets and shaped clusters.

Kerning is a positioning feature, not ligature substitution

Kerning adjusts spacing or glyph placement for combinations such as AV; it does not necessarily combine those glyphs into one. A ligature can affect glyph count, while kerning usually changes advances or offsets. OpenType can express both through independent structures and feature controls.

For reproducible rendering tests, compare glyph IDs and positions separately. If disabling kern alters spacing but preserves glyph IDs, the system is behaving as expected. If disabling liga changes glyph sequence and caret opportunities, that is a different phenomenon.

Complex scripts require more than Latin heuristics

Arabic contextual forms and several Indic orthographic behaviors involve script-specific substitutions and reordering. A tester who validates only Latin fi may miss serious shaping failures. In some scripts, mandatory shaping is required for legibility, not simply improved visual polish.

Shaping engines coordinate script-specific rules, character properties, language tags and font lookups. A raw GSUB feature list is not a substitute for applying Unicode character analysis or segmentation correctly, and testing a feature in isolation may not reproduce a real user-facing run.

Preserve semantics in fancy and decorative output

Do not substitute a presentation-form scalar merely to force a ligature when editable Latin letters are intended. Conversely, styled Unicode mathematical symbols are actual encoded characters, not just font toggles. For example, U+1D41F MATHEMATICAL BOLD SMALL F remains a distinct character from U+0066.

When experimenting with Unicode styled text, inspect the resulting code points and test copy/paste separately from visual rendering. A copied ligature created by a font is generally still the original letters; a copied compatibility character may behave differently under NFKC and in search.

Reproducible experiment: preserve the input while comparing the output

The following specimen is deliberately small enough to audit manually. For any test involving rendering, also record the exact font files, shaping configuration, user locale and platform versions. The code prints or illustrates source-level facts; it does not claim that JavaScript can identify a platform's selected font or glyph IDs without the relevant layout instrumentation.

const plain = 'fi';
const presentation = '\uFB01';
console.log([...plain].map(c => c.codePointAt(0).toString(16))); // 66,69
console.log([...presentation].map(c => c.codePointAt(0).toString(16))); // fb01
console.log(presentation.normalize('NFKC') === plain); // true
// CSS: font-variant-ligatures: common-ligatures;
// CSS: font-feature-settings: 'dlig' 1; (only if font supports it)

A useful report includes both positive and negative evidence. Record what stayed identical as well as what changed: identical scalar values with different glyphs indicate a presentation-layer divergence, whereas differing scalars reveal a transformation, selection or interchange problem. Preserve the original code points before applying normalization or conversion.

Do not correct a visual artifact by silently rewriting the user's Unicode string, stripping default-ignorable characters without context, replacing unknown scalars with question marks, or flattening rich text without consent. Data integrity, rendering aesthetics, selection behavior and search policy have different constraints. A fix at one layer can create regressions in another.
