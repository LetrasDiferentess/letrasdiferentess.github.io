Unicode Text in Spreadsheet Import/Export: CSV, TSV, Encodings and Data Fidelity

A detailed guide to UTF-8 CSV and TSV exchange, BOM detection, quoted line breaks, spreadsheet type inference and preserving Unicode data across imports and exports.

Technical referenceUnicode and web interoperabilityUpdated 26 October 2026

A spreadsheet is a typed grid, while CSV and TSV are text-based interchange formats. Import pipelines must parse bytes, delimiters, quoting and cell values before the spreadsheet applies automatic type inference. A failure at any layer can change Unicode characters, leading zeros, date-like identifiers or multi-line fields.

Specify the physical encoding independently of the CSV grammar

CSV describes records and separated fields, not a universal encoding auto-detection algorithm. For a controlled modern interchange, explicitly use UTF-8 and document that choice. UTF-8 byte sequences for non-ASCII characters must be decoded before any string-level quoting or delimiter interpretation.

A UTF-8 BOM (EF BB BF) can act as an interoperability signature for certain spreadsheet applications, but it is not required for UTF-8 and some tools treat it as part of the first header field. Test the intended import software and decide whether to include it. A BOM does not change the Unicode string's normalization form.

Use quoted fields for commas, quotes and newlines

Under RFC 4180-style CSV, a field containing the delimiter comma, a double quote or a record-breaking newline is normally wrapped in double quotes; a literal quote within a quoted field is represented by two consecutive double quotes. A simple line.split(',') parser therefore breaks on valid input.

Record separators are traditionally CRLF in RFC 4180, but real files also contain LF. If an exporter writes a newline inside a quoted cell, the importer must not interpret it as the end of that record. Use a well-tested CSV parser rather than a single regular expression.

TSV does not eliminate all escaping questions

Tab-separated values are convenient for copying rectangular ranges, but a cell containing a literal tab or newline still requires a documented serialization rule. Applications differ in whether they use CSV-like quoting, clipboard-specific formats or unsupported characters.

Do not assume that TSV from an operating-system clipboard is byte-for-byte identical to a file exported as TSV. The clipboard may also include an HTML table representation, and the importing spreadsheet may prefer that over plain text.

Preserve leading zeros and identifier spelling

A cell containing 00123 may be interpreted as the number 123, discarding its lexical form. Long digit sequences may be rounded under spreadsheet numeric representations. Date-like strings, scientific notation and Unicode numerals can also trigger locale-dependent coercion.

If values are identifiers, import them as text using an explicit schema or column type. A number cell with a custom display format is not the same as preserving the underlying Unicode string. Validate the exported scalar sequence after a full spreadsheet round trip.

Formula injection is a separate security boundary

Spreadsheet applications may treat input beginning with = or other formula-introducing prefixes as active formulas, depending on product and import path. A CSV export of untrusted fields should implement a destination-specific strategy to keep the field as data rather than an executable formula.

A leading apostrophe, quoting, or added whitespace has different effects across products; no universal one-character workaround is guaranteed. Document the tradeoff between safety and exact data round trips. Validate with the target spreadsheet and user workflow, not merely by inspecting the CSV's quoting.

Normalization and invisible characters can change matching

A spreadsheet may retain U+00E9 and U+0065 U+0301 as distinct underlying strings even if both appear as é. Unicode normalization policy affects equality and deduplication across tools. Nonbreaking spaces, bidirectional controls and zero-width characters may be invisible but still alter searches.

Use code-point or escaped-byte audits on suspicious cells. When normalizing for a downstream matching task, preserve the original field separately if reversibility matters. Compatibility normalization is not a harmless visual cleanup for mathematical alphabets or styled Unicode.

Locale affects numeric and date parsing, not Unicode validity

A decimal comma or localized date convention may be interpreted differently according to spreadsheet locale and configured import options. This can happen even when every UTF-8 byte is correctly decoded. Treat locale-aware coercion as a post-decoding transformation.

A reliable ETL process specifies decimal separators, date formats and column types independently of text encoding. Round-trip tests should assert both the scalar value and the intended cell data type.

Emoji and supplementary characters require UTF-aware pathways

A Unicode scalar above U+FFFF, such as U+1F600 GRINNING FACE, occupies four bytes in UTF-8 and two UTF-16 code units in JavaScript. Tools counting character positions by bytes or code units can truncate an output cell mid-sequence.

Count code points or grapheme clusters only for the metric actually required. Rendering a glyph is outside the CSV format's responsibilities. Emoji artwork or fallback boxes in a spreadsheet do not by themselves imply that the exported Unicode scalar changed.

Design an end-to-end interchange conformance test

Export a fixture containing commas, double quotes, CRLF inside a quoted field, Unicode accents, mathematical symbols, emoji, leading-zero IDs, dates and formula-like text. Capture raw output bytes; import with explicit settings; inspect the resulting cell types and values; then export again.

Compare original and final values under both exact and intentionally normalized policies. Report data type inference, encoding errors, visual fallback and CSV quoting defects as separate categories. Only label the pipeline lossless when the tested fields satisfy the actual promised contract.

Reproducible example and limits of the measurement

The following specimen demonstrates the specific concept in a controlled source or browser context. It is not a substitute for fully exercising the target application with the appropriate language, platform input method and real user data. Distinguish textual transformations from display-only differences.

const csv = '"name","notes"\r\n"José","a ""quoted"" word,\nthen a new line"\r\n';
const bytes = new TextEncoder().encode(csv);
console.log([...bytes.slice(0,14)]); // UTF-8 bytes, not a CSV parser
console.log(new TextDecoder('utf-8',{fatal:true}).decode(bytes)===csv);
